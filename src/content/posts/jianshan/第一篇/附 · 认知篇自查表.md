> **不要把「上次有效」当成「这次也有效」。**

这些问题是给判断之前用的。不必每次都问一遍，但在你准备拍板，或者准备拒绝一件事之前，值得先过一眼：

| 自查问题 | 如果答不清楚，先不要急着做什么 |
| --- | --- |
| **惯性——我是不是又在重复自己** |  |
| 这次的判断，来自新情况，还是上一次成功的惯性？ | 不要把「上次有效」当成「这次也有效」 |
| 这件事是「必须做」，还是「因为大家都觉得该做」？ | 不要用行业趋势替代用户问题 |
| 它有没有让产品偏离原本的定位，或者背上一个新目标？ | 不要让一个工具同时背太多指标 |
| **证据——我看见的是事实，还是我想看的东西** |  |
| 我说的「用户」，具体到角色、场景和任务了吗？ | 不要用抽象人群替方案背书 |
| 这条判断最强的证据是什么：观点、回忆、现场动作，还是结果验证？ | 不要把强度不同的证据混成一句「用户反馈」 |
| 数据冒出来的位置，就是问题发生的位置吗？ | 不要只修指标跳出来的那个页面或环节 |
| 用户说的方案，是不是现有系统里的一个补救动作？ | 不要把补救动作直接做成产品答案 |
| 用户离开产品之后，还去了哪些系统、表格、群聊或线下流程？ | 不要把产品里的路径当成任务全貌 |
| 现在用来裁决这件事的指标，覆盖了它的全部价值吗？ | 不要在单一指标上分胜负 |
| **代价——谁在为这个决定付账** |  |
| 用户为这个问题付出了什么：时间、等待、返工，还是担责？ | 不要把抱怨和偏好当成真实痛点 |
| 这个方案的主要代价由谁承担？长期成本由谁背？ | 不要只看收益，不看代价有没有被转移 |
| 哪些损失一旦发生就补不回来？ | 不要先追最优解，先挡住不可逆的损失 |
| 这件事跑出来的结果，最后谁使用、谁确认、谁担后果？ | 不要只看界面上那个操作者 |
| **回退——错了以后，我能不能退回来** |  |
| 什么信号出现时，说明我的判断该被推翻？ | 不要把一次拍板固化成永久结论 |
| 上线后用什么证明问题被解决了，而不是功能被完成了？ | 不要把发布当成终点 |
| 如果做错了，能不能体面回退？ | 不要把可逆的事当成不可逆的做 |
